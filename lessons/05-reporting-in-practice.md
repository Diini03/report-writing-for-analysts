# Lesson 5: Reporting in Practice

## Where reporting lives inside BI tools

Business intelligence tools such as Power BI, Tableau, and Looker are built primarily for interactive exploration of data, not for extended written narrative. Attempting to fit the entire six part report structure from Lesson 3 into on screen text generally makes a dashboard harder to read rather than easier. For this reason, most professional workflows pair the two formats: an interactive dashboard for exploring what happened, alongside a separate written document, typically a PDF, Word file, or written summary, that carries the explanation and recommendation.

Stating this pairing directly, when asked how reporting fits into a BI tool, reflects sound judgment rather than a gap in tool knowledge. That said, most BI platforms do provide features intended to carry narrative directly within the dashboard itself.

| Feature                         | Typical use                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------- |
| Text annotations beside visuals | A brief explanation placed next to the chart it refers to                       |
| Tooltips or hover detail        | Additional context behind a specific figure, without cluttering the main view   |
| Guided navigation between views | A fixed sequence of screens that leads the reader through the findings in order |
| A dedicated summary page        | A page styled as a written summary, placed at the front of the report file      |
| Paginated or print style export | A formal, print ready version generated from the same underlying data           |

A dashboard that includes at minimum a short annotation beside its key visuals, and a summary page at the front covering the same ground as the summary and key findings sections from Lesson 3, generally meets the expectation of a report built inside a BI tool.

## Communicating a report verbally

Analysts are frequently asked to describe how they would report on a dashboard as a spoken interview question rather than a written exercise. This tests something different from writing ability. It tests whether the analyst has a repeatable method for moving from data to a decision, one that can be demonstrated on the spot without prepared material.

A small number of habits distinguish a strong verbal answer from a weak one.

**Naming the report type before describing content.** Stating that a situation calls for a diagnostic or recommendation type report, before describing findings, signals a structured approach rather than an improvised one.

**Ending on an action.** A verbal answer that only describes the dashboard has not answered the underlying question. The strongest answers conclude with a stated recommendation, even a provisional one.

**Including a number, even a hypothetical one.** In a scenario without real data available, stating an assumed figure and reasoning from it demonstrates the analytical process being tested, which matters more in this context than the accuracy of the specific number.

**Stating an approach when the answer is unknown.** Rather than stopping at a lack of information, describing what would be checked first keeps the answer productive. For example, stating that the first step would be to check whether an issue is isolated to one region or occurring company wide demonstrates a method, even without the underlying data in hand.

**Prioritizing the most likely explanations.** Listing every conceivable cause for an observed change suggests an inability to prioritize. Identifying the one or two most probable explanations, and describing how each would be confirmed or ruled out, demonstrates stronger judgment.

**Acknowledging a limitation.** A single, direct statement of uncertainty, such as noting that a data quality issue should be ruled out before acting on a finding, reflects sound analytical practice rather than a weakness in the answer.

## A complete verbal answer

Combining these habits produces an answer of this form, when asked how a report would be prepared following a dashboard:

> The type of report would depend on the situation, though most cases call for a combination of diagnostic and recommendation reporting. I would identify two or three key findings directly from the dashboard, each supported by a figure. I would then explain the likely cause behind those figures rather than restating what the dashboard already shows, and close with a specific recommendation along with one limitation of the analysis. Within the BI tool itself, I would typically include a short summary page and brief annotations beside the key visuals, and export a fuller written version for stakeholders who require additional detail.

This answer demonstrates the full course in a single response: classification of the report type, quantified findings, interpretation, a specific recommendation, and an acknowledged limitation.

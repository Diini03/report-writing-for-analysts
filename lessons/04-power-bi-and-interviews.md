# Lesson 4: Reports Inside Power BI, and Getting It Right in an Interview

## Say the honest thing first

Power BI is built for exploring data, not for writing prose. Forcing the full six part skeleton into text boxes usually makes a dashboard worse, not better. Most real workflows pair the two, a dashboard for what happened, a separate written document for why and what next. Saying that pairing out loud in an interview is a real answer, not a dodge.

## The tools Power BI actually gives you

| Feature                      | What it's good for                                     |
| ---------------------------- | ------------------------------------------------------ |
| Text box next to a chart     | One or two lines of explanation, the minimum bar       |
| Tooltip page                 | Context behind a single number, on hover               |
| Bookmarks and selection pane | A guided sequence of views, forcing a reading order    |
| A narrative first page       | The full summary and findings, written inside the file |
| Report Builder               | A separate tool for pixel perfect, printable documents |
| Export to PDF or PPT         | The most common real world handoff                     |

**Your turn.** Pick one Power BI dashboard you've already built. Which one feature from the table above would help it most right now, and where exactly would you put it.

## What a strong interview answer sounds like

> The dashboard carries a short summary page and text box notes next to the key charts. For a formal audience, I'd export that alongside a written document covering the explanation and recommendation, the parts that don't fit naturally inside dashboard text.

## The real trap behind these questions

Nobody is really asking you to perform a finished report from memory. They're checking whether you have a repeatable way of thinking, one you can walk them through out loud.

## Six mistakes, and the fix

**Jumping straight to "I'd make a report," nothing behind it.**

> Fix: name the type first, diagnostic, recommendation, whatever fits, then walk through the shape.

**Describing the dashboard instead of answering the scenario.**

> Fix: always land on an action, even a rough one. An imperfect recommendation beats a perfect description.

**No number anywhere in the answer.**

> Fix: invent a plausible number even in a made up scenario. The interviewer cares about the reasoning path more than the exact figure.

**Freezing on "I don't know."**

> Fix: say what you'd check first. "I don't have that number here, but I'd start by checking if this is one region or company wide, since that tells me if it's local or systemic."

**Listing every possible cause.**

> Fix: give your top one or two, mention the rest exist, explain how you'd rule them in or out.

**No hint of uncertainty anywhere.**

> Fix: one honest line. "I'd want to rule out a data quality issue before acting on this."

**Your turn.** Make up your own scenario question, something like "what would you do if signups suddenly dropped." Answer it out loud, using the six fixes above, before reading the model answer below.

## The full answer to your actual interview question

> I'd first figure out what kind of report the situation calls for, usually some mix of diagnostic and recommendation. I'd pull two or three key findings straight from the dashboard, each with a number attached. Then I'd explain the likely reason behind those numbers, not just repeat what the chart already shows. I'd end with a specific recommendation, and note one limitation, like a gap in the data. If it's inside Power BI, I'd usually put a short summary on the first page and export a fuller written version for anyone who needs more depth.
